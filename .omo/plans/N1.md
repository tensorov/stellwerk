## Цель

`stellwerk run <task.toml>` выполняет ОДИН реальный запуск:
конфигурация → отказ без неё → процесс в bwrap с `env_clear` →
блокирующая авторизация ДО каждого защищённого вызова → `gateway::decide` →
receipt в SQLite → Pi-поток разобран в `RunOutcome` → evidence-цепочка →
статус «ждёт человека» → вывод в терминал.

**Done/PASS не объявляются** — приёмка остаётся за человеком.

### Что не так

Риск инструмента **объявляет вызывающий**, а реестр в решении не участвует:

- `crates/stellwerk-cli/src/main.rs:141-150` собирает
  `Call { tool: "fixture", module: "stellwerk-cli", risk: ToolRisk::Classified(RiskClass::R0) }`
  — класс риска **захардкожен**. Комментарий в коде признаёт это и обходит:
  «`risk_for` реестра его не знает и дал бы `Unclassified`, а неизвестное в
  неинтерактивном прогоне обязано стать отказом».
- `crates/stellwerk-task/src/runner.rs:279-290` — `authorize` копирует `call.risk`
  в `CallRequest` без сверки с реестром.
- `orchestrator.rs` — `preflight()` зовёт `risk_for` и кладёт результат в
  `GateRecord`, но эта запись **никогда не читается**.

Следствие: «риск берётся из реестра кода» верно для `risk_for()` и для
записанного гейта, и **ложно для самого решения** Allow/Deny. Это тот же дефект
самодекларации, который закрывал N1-06 — сменился только объявляющий: было
`modules.toml`, стал CLI.

Подтверждено: фикстура `crates/stellwerk-task/tests/authorization.rs:66-69`
использует `tool: "bash", module: "fs"`; в реестре только `polyforge`,
`gate_report`, `gate_evaluate`. `bash`/`fs` в реестре отсутствуют.

### Почему не починено внутри пакета

Ни одна честная реализация не помещается в объявленный scope:

| Вариант | Что даёт | Цена |
|---|---|---|
| **A** — проверка согласованности на границе запуска (`orchestrator.rs`) | реестр становится обязательным; сохраняет инвариант `authorize == decide` (F-10) | ломает 3 теста в `tests/authorization.rs` — фикстура объявляет R0 для незарегистрированного `bash`/`fs`. Нужен **1 файл вне scope** |
| **B** — риск выводится из реестра внутри `authorize` | реестр — единственный источник на точке решения | ломает **3 тестовых файла** (`permission_wire`, `authorization`, `vertical`), включая F-10-guard, чья матрица держится на незарегистрированных классах |
| **C** — заморозить scope, разбить на два пакета | границы соблюдены | N1 не закрывается в этом заходе |

Расширять `forbidden_touch` без решения владельца оркестратор не вправе:
дисциплина существует именно для того, чтобы исполнитель не мог расширить
границы сам.

### Что нужно от владельца

Один выбор: **A** (1 файл вне scope), **B** (3 файла, осознанный размен F-10)
или **C** (разбить на пакеты).

### Уточнение 2026-10-11: спецификация владельца несовместима сама с собой

Проверено чтением всех трёх запрещённых тестовых файлов. Факты:

| файл | инструмент | объявляемые классы | что требует |
|---|---|---|---|
| `permission_wire.rs:217` | (матрица RISKS) | R0..R5 | `authorize(call) == decide(as_request(call))`, где `as_request` копирует **`call.risk`** |
| `vertical.rs:77` | `bash` | R0, R2, R5 | разные вердикты на каждый класс |
| `authorization.rs:68` | `bash` / `fs` | R0, R5 | R0→Allow+spawn, R5→Deny |

`bash` и `fs` **отсутствуют** в реестре (`TOOL_REGISTRY` содержит только
`polyforge`, `gate_report`, `gate_evaluate`).

Следствие: любой механизм, при котором класс реестра управляет решением, для
одного и того же инструмента схлопывает шесть объявленных классов в один и
ломает все три файла.

- Механика владельца (`authorize` берёт risk из registry lookup, критерий
  `R4 → Ask`) **несовместима** с запретом трогать эти три файла. Это цена
  варианта B, который владелец отверг.
- Вариант A1 (отказ на границе запуска, `authorize` не трогаем) оставляет
  `permission_wire` зелёным, но **не выполняет** критерий `R4 → Ask`: при A1
  отказ приходит вместо `Ask`, и вердикт остаётся вычисленным из объявления.

Итог: заявленные критерии нельзя выполнить одновременно с запретом на эти
три файла. Требуется либо снять запрет (B), либо смягчить критерий `R4 → Ask`
до проверки реестра в связке с `decide` напрямую (A1).
