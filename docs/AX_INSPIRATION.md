# AX_INSPIRATION — что берём из google/ax, а что нет

Дата: 2026-09-26. Статус: канонический документ заимствований.
Источник идей: **AX (google/ax)**. Это источник форм, а не зависимость и не основа.

AX полезен тем, что доводит до конца одну мысль: **задача, её рабочее место, модель и
прогон — это разные сущности с разными жизненными циклами.** Большинство агентных
систем сливают их в один объект и потом не могут ни объяснить, куда ушли токены, ни
доказать, что было сделано. Мы берём разделение и формы команд, а не инфраструктуру.

## 1. Task — единица работы

```
TaskSpec {
  id,                    // стабильный идентификатор, по нему идёт evidence
  goal,                  // чего добиться, одной фразой
  workspace_ref,         // где работать (см. WorkspaceSpec)
  model_ref,             // кем работать (см. ModelBinding)
  packet,                // сам текст задания для исполнителя
  limits,                // потолки: файлы, строки diff, время, ретраи, контекст
  evidence_policy,       // чем доказывать выполнение
}
```

Принципы, которые берём:

- **limits — часть задания, а не настройка рантайма.** «Не больше 3 файлов и 200 строк
  diff» — это свойство задачи, а не просьба к воркеру.
- **evidence_policy задаётся до старта.** Нельзя узнать post factum, что «достаточно».
- **Жизненный цикл явный и типизированный:**
  `Draft → Planned → Reviewed → Delegated → Running → Suspended → EvidenceSubmitted →
  Verified → Validated → Done | Failed | Blocked`.
  Переходы — единственное место, где живёт правило «что считается продвижением».
- `Blocked` — первоклассный статус. Задача, которой не хватило данных или контекста,
  не должна выглядеть как `Failed`: их различение экономит месяцы разборов.

## 2. Workspace — рабочее место

```
WorkspaceSpec {
  id,
  base_commit,           // одно число вместо ветки: воспроизводимость
  repos,                 // какие репозитории видны
  tools_allow,           // что можно вызывать
  tools_deny,            // что нельзя никогда (deny важнее allow)
  mcp_servers,           // какие MCP-серверы поднимать
  network_policy,        // Deny | AllowList | Allow
  env,                   // явное окружение (без секретов)
}
```

Принципы:

- **`base_commit` вместо «текущей ветки».** Результат всегда привязан к коммиту.
- **Политика сети — типизированная, а не «сеть есть/нет».** `Deny` по умолчанию для
  воркеров; `AllowList` — для задач, которым нужен конкретный хост.
- **Инструменты разделяются на allow/deny.** Deny выигрывает: `rm *`, `opencode debug
  config*` и подобное запрещаются независимо от того, что в allow.

## 3. Model — привязка модели

```
ModelBinding {
  id, provider, model_id,
  data_class,            // Public | Internal | Personal — маршрутизация, см. ниже
  context_window, max_output,
  budget_tokens_per_task,
}
```

Принципы:

- **`data_class` маршрутизирует, а не документирует.** `Personal` не должен уехать в
  модель с чужим retention. Это проверяемое правило, не комментарий.
- **Окно и бюджет — часть привязки.** Планер на 200k нельзя назначить задаче с
  бюджетом 43k: это ошибка планирования, а не ошибка воркера.
- **Cost измеряется, а не оценивается.** У нас это `measure`: байты схем × калибровка.

## 4. Run — исполнение

```
Run = sandbox(WorkspaceSpec) → поток событий → receipts в PolyForge → статус
```

Принципы:

- **Песочница создаётся из `base_commit`, а не копируется из рабочей копии.** У нас это
  `git archive` в `/tmp` без `.git` — в песочнице физически нечего указать на хост-репо.
- **Прогон не равен задаче.** У задачи может быть несколько прогонов (ретраи).
- **Прогон либо даёт evidence, либо не даёт.** «Exit 0 от агента» не является
  доказательством: это наш validity gate (`stop_reason`, `tool_steps`, `turns`,
  timeout).
- **Тип отказа — часть результата.** `FAILED(loop)` (сработал loop-guard) и
  `FAILED(measure)` — разные диагностики, и сводить их к «модель не справилась» нельзя.

## 5. Формы команд (kubectl-shaped)

| AX | Наша форма | Смысл |
|---|---|---|
| `ax apply -f task.yaml` | `stellwerk task apply <file>` | создать/обновить TaskSpec |
| `ax get task/<id>` | `stellwerk task get <id>` | прочитать спецификацию и статус |
| `ax watch task/<id>` | `stellwerk task watch <id>` | события прогона в реальном времени |
| `ax suspend task/<id>` | `stellwerk task suspend <id>` | остановить, сохранив состояние |
| `ax resume task/<id>` | `stellwerk task resume <id>` | продолжить с последней точки |

Что берём: **форму команд** — kubectl-shaped интерфейс дисциплинирует: один глагол
на действие, `-o json` для машинного чтения, отсутствие «комбо-команд». Что берём
дословно: разделение `apply` (спецификация) и `run` (исполнение).

## 6. Чего НЕ берём из AX

| Не берём | Почему |
|---|---|
| Kubernetes | Наша федерация не нуждается в оркестраторе контейнеров на старте; K8s — это отдельный класс сложности (etcd, control plane, RBAC-поверх-RBAC) при нулевом выигрыше для ноутбука + двух серверов |
| Agent Substrate | Собственный рантайм агентов. У нас исполняет Pi/OMP — исполняемые сменные |
| Redis control plane | NATS JetStream закрывает потребность в очередях; Redis — ещё одна зависимость и ещё один режим отказа |
| billions scale | Проектируем под десятки параллельных прогонов на ноутбуке. Преждевременная оптимизация распределённости ломает local-first |

## 7. Наша реализация (что это значит на практике)

- **Local-first.** `stellwerk task apply/watch` работают на ноутбуке без сети. Сеть —
  ускорение синхронизации (NATS leaf), а не условие работы.
- **Изоляция растёт в три шага:**
  1. сейчас — `git archive` в `/tmp`, path-guard, отсутствие `.git` (достаточно, чтобы
     поймать F1-сценарий; ловится пост-фактум и блокируется экспорт);
  2. затем — podman/bubblewrap, когда появится потребность в сетевой политике уровня
     syscall;
  3. удалённый исполнитель — тот же контракт, другое transport.
- **API, совместимый с будущим remote.** Локальный SQLite и серверный Postgres
  реализуют одни и те же трейты (`TaskStore`, `EventStore`, `ModuleStore`), поэтому
  переезд на remote не меняет вызывающий код.
- **События — единственный поток.** UI, отчёты и метрики читают поток событий, а не
  внутренние структуры. Это делает Board/Inbox/CRM проекциями, а не интеграциями.
- **Политика как код.** RiskClass → permission (allow|ask|deny), data_class → модель,
  network_policy → изоляция. Каждое правило имеет тест.

## 8. Что осталось спорным

- **Watch-источник.** Прямой поток событий против опроса по store. Пока тривиально:
  watch читает `EventStore.list_since` и печатает дельту.
- **Suspend/resume для Pi.** У Pi есть своя сессия; «продолжить с последней точки»
  для воркера может означать новый процесс с тем же prompt и тем же base_commit.
  Семантика не зафиксирована — см. M2.
- **Multi-user на ноутбуке.** PolicyLevel задан, но локально всё работает от одного
  пользователя. Реальная проверка — на сервере с RLS.
