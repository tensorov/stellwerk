   Прежняя формулировка сохраняется как свидетельство:

   > `pub fn next_status(verdict: &CallVerdict, risk: ToolRisk) -> TaskStatus` — маппинг
   > вердикта в статус:
   > - `Ask` в неинтерактивном прогоне → `TaskStatus::Suspended`, **через предикат
   >   `TaskStatus::can_transition_to`**, без собственного свода переходов;

   ```rust

       /// Вердикт не меняет статус задачи; вызывающий в БД не пишет.
       Keep,
       /// Вердикт требует перехода; вызывающий проверяет `can_transition_to` и пишет.
       Transition(TaskStatus),
   }

   pub fn next_status(verdict: &CallVerdict, risk: ToolRisk) -> StatusEffect
   ```

## Изменение сигнатуры `next_status`: причина — противоречие `Allow`/«без смены» (2026-10-01)

**Противоречие, ради которого изменение.** Прежняя сигнатура требовала `-> TaskStatus` и
одновременно требовала для `Allow` «без смены статуса». Без параметра текущего статуса
«без смены» невыразимо: функция обязана что-то вернуть, а возврат `TaskStatus` сам по себе
и есть смена. Три прочтения давали три разных API и три разных места вызова, а выбрать одно
молча — значит решить семантику контракта без владельца.

**Решение владельца — именованный тип, а не `Option`.** Логика «вернуть значение, которое
вызывающий обязан обработать» верна, но `None` — плохое имя: в этом проекте отсутствие
значения уже трижды оказывалось ловушкой (F-10, F-30, `unwrap_or(R0)`), потому что читается
как «неизвестно». Здесь же это сознательное «оставить как есть», и два разных смысла в одном
`None` — тот же закон 6 с другой стороны. Поэтому `StatusEffect { Keep, Transition(TaskStatus) }`
использует уже существующий в проекте паттерн именованных состояний (`Unclassified`,
`NotApplicable`).

**Что это снимает помимо `Allow`.** Прежний текст требовал переход «через предикат
`can_transition_to`» внутри `next_status`, и одновременно требовал `Suspended` → `Suspended`,
что предикат запрещает как переход в самого себя. Противоречие исчезает, когда читать пару
`Suspended` → `Suspended` как «вердикт `Suspended` даёт статус `Suspended`», а не как переход
статуса в себя. `next_status` вычисляет цель и **не знает текущего статуса**; единственный
источник текущего статуса — `status_of` (F-13), то есть он у вызывающего. Это и объясняет,
почему его нет в сигнатуре.

**Не contract-change ядра.** Тип живёт в `stellwerk-task`, `contract.rs` не трогается, лимит
файлов не превышен. Это правка текста задания под фактически реализуемую семантику — тот же
класс, что M2-04/M2-05.

**Обязательный тест, который не даст «без смены» снова стать обещанием.** `Allow` → `Keep`
проверяется не только по значению эффекта: после `Keep` вызывающий в БД не пишет, поэтому
`status_of` до и после обязаны совпасть. Без второго утверждения `Keep` означал бы «мы решили
ничего не делать», что неотличимо от «мы забыли».
