# ADR-0028: проверка артефактов публикации — исполняемая приёмка, не Rust integration test

Статус: принят
Дата: 2026-11-22
Пакет: publication-readiness / task-2
Связано: ADR-0025 (метаданные публикации); ADR-0006 (PolyForge/Riegel);
AGENTS.md — протокол завершения (RED/GREEN/PROOF)

## Проблема

Публикационная подготовка добавляет артефакты, которые не являются поведением
Rust-кода: тексты лицензий, документы, метаданные манифеста, наличие ADR.
Для них нужно выбрать способ проверки. Два наивных пути плохи:

1. **Декларация в тексте.** «Файл добавлен, значит готово» — не проверка: файл
   может быть пустым, содержать неверный copyright, потерять ключ метаданных
   или исчезнуть при последующей правке.
2. **Rust integration test по инерции.** ADR-0006 требует, чтобы проверка
   проходила через PolyForge/Riegel, когда речь идёт о верифицируемом поведении
   кода/контракта. Применять это правило к статическим артефактам публикации
   буквально — значит строить тяжёлый harness вокруг проверки существования
   файла и строк, не получая реальной гарантии сверх обычной команды.

Нужна граница: где заканчивается исполняемая приёмка артефакта и начинается
область ADR-0006.

## Решение

1. **Лицензии, документы и метаданные публикации проверяются исполняемой
   приёмкой.** Приёмка — это точные команды, записанные в плане/пакете и
   воспроизводимые агентом: `test -s`, `rg -q`, `python3 -c ... tomllib ...`,
   `cargo metadata --no-deps --format-version 1`, и аналогичные проверки
   наличия/содержимого/машиночитаемости.

2. **Новый Rust integration test для этих артефактов не создаётся.** Если
   свойство выражается проверкой файла, текста или метаданных манифеста, оно
   покрывается командой приёмки, а не `#[test]`/integration test в crate.

3. **ADR-0006 (PolyForge/Riegel) здесь не применяется.** ADR-0006 управляет
   верификацией поведения и контрактов, где нужен attestation/verification
   контур. Статические публикационные артефакты не являются таким поведением;
   их корректность доказывается воспроизводимым выполнением команд приёмки.

4. **Приёмка должна быть наблюдаемой.** Для пакета фиксируется RED (команда
   падает до изменения) и GREEN (та же команда проходит после изменения), а
   результат сохраняется в evidence. «Файл на месте» без вывода команды не
   считается доказательством.

5. **Граница пересекается только при появлении поведения.** Если публикационный
   артефакт начинает порождать проверяемое runtime/build-поведение (генератор,
   валидатор, контрактный парсер, gate), для этого поведения применяется
   обычный TDD/verification контур проекта, включая ADR-0006 там, где он
   релевантен.

## Последствия

- Планы публикационной готовности могут содержать acceptance-команды как
  основной механизм доказательства для документов и метаданных.
- Evidence по таким пакетам включает вывод RED/GREEN и точные команды, чтобы
  проверка была воспроизводима без чтения чата.
- Отсутствие Rust-теста для LICENSE/README/ADR/manifest metadata не является
  пробелом покрытия, если есть исполняемая приёмка.
- Приёмка не подменяет code review: команда проверяет заявленное свойство, но
  не оправдывает ложное содержимое, прошедшее по слабому паттерну.

## Что запрещено

1. Объявлять статический артефакт проверенным без выполнения команды приёмки.
2. Добавлять Rust integration test только ради формального соответствия ADR-0006
   для файла/метаданных, не имеющих runtime-поведения.
3. Использовать этот ADR как оправдание для пропуска TDD/attestation там, где
   меняется код, контракт или исполняемое поведение.
4. Подменять RED/GREEN рассуждением «очевидно пройдёт».
5. Прятать провал приёмки за `|| true`, `continue-on-error` или ручную пометку
   «ok».

## Когда пересматривается

Если публикационные артефакты станут входом исполняемого валидатора, CI-gate
или runtime-контракта, либо если проект введёт единый harness для
документарных проверок, этот ADR пересматривается отдельным `contract-change`
пакетом. Пересмотр обязан сохранить различие между проверкой артефакта и
проверкой поведения.
