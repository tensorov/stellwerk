## Контекст

- **Что не работает сейчас.** Приёмка RED-пакета инвертирована: `! cargo test` → exit 0.
  Но `evidence_verify` считает ненулевой код возврата провалом инструмента, поэтому
  попытка аттестовать `cargo test --test session_contract` вернула
  `ToolFailed { exit_code: 101 }` — то есть ровно то поведение, ради которого пакет
  и писался. Подтверждается только компиляция (`--no-run`), а свойство «тест
  падает» остаётся утверждением модели. Затронуты M3-11a (гейт `a08d94c4…`) и
  каждый RED-пакет дальше.
- **Форма, предложенная в решении, в код не вписывается.** Запись allowlist — тройка
  `{ name, bin, args }` с **фиксированным** вектором аргументов (F-08, issue #1:
  `crates/polyforge-toolrunner/src/runner.rs:123`). Фиксированный вектор значит, что
  имя бинарника в него не входит и передать его нельзя. Отсюда пер-бинарные записи
  вынуждены **устройством allowlist**, а не вкусом.
- **Второй инвариант, независимый от allowlist.** Шапка `xtask/src/main.rs` запрещает
  перенаправлять что-либо из `argv` в дочерний процесс: иначе
  `cargo xtask red-gate-x --exec=/bin/false` исполнил бы произвольное, то есть дыра,
  ради закрытия которой xtask и написан. Поэтому задача — **литерал** в `match`, а
  путь к набору — **константа** в исходнике. Форма `red-gate <имя>` нарушила бы и это.
- **xtask не аттестуем, пока не смержен патч F-08.** Обёртка станет пригодной для
  `evidence_verify` только после мержа `feat/allowlist-cargo-xtask` и `cargo install`
  в репозитории PolyForge. До этого она локально проверяема, но не аттестуема — и это
  надо сказать прямо, а не выдавать за готовую аттестацию.

## Что сделать

1. **Вторая таблица рядом с `TASKS`, не вместо неё:** `RED_GATES: &[(&str, &[&str])]`,
   где имя задачи — литерал, а значение — константный вектор аргументов `cargo test`.
   Каждый RED-бинарник проекта получает свою строку: `red-gate-session-contract`,
   `red-gate-session`, `red-gate-session-failure`, `red-gate-permission` и далее по
   мере появления пакетов. Ключевая строка и есть та фиксированная точка входа,
   которую allowlist сможет зафиксировать.
2. **Логика в трёх шагах, порядок обязателен:**
   1. `cargo test … --no-run` — обязан завершиться успехом. Не собралось →
      отказ: подтверждать падение теста, который не собрался, нечего.
   2. `cargo test …` — обязан завершиться **неуспехом**. Успех → отказ: тест зелёный,
      значит он не держит RED-спецификацию.
   3. Оба условия выполнены → `ExitCode::from(0)`.
   Никакого вывода в stdout: аттестуется код возврата, а не текст.
3. **Отказ — с внятной причиной в stderr**, иначе диагностировать провал придётся
   повторным прогоном. Три разных сообщения для трёх разных причин, а не одно
   «красный гейт не прошёл»: не прошла сборка / тест не упал / упал не так.
4. **Не расширять `TASKS`.** Обычные задачи пробрасывают код как есть; инверсия — это
   другой смысл кода, и смешивать их в одной таблице значит сделать таблицу
   зависимой от флага, который легко потерять.
5. **Ничего из `argv` не перенаправлять.** Сейчас это уже так (`std::env::args().nth(1)`
   используется только для выбора литерала) — не сломать это. Имя задачи подставляется
   в сообщение через `{name:?}`, как сейчас, а не в строку команды.
6. **Тесты в `xtask/tests/xtask_cli.rs`** — новый файл, интеграционный, через
   `env!("CARGO_BIN_EXE_xtask")`. Обязательные случаи: неизвестная задача → 2;
   попытка пробросить `--exec=…` → задача всё равно не исполняет его; зелёный
   бинарник в `RED_GATES` → ненулевой код; красный → ноль; вызов без аргументов → 2.
   Именно тесты на невыразимые случаи, а не на счастливый путь.
7. **Ни одного теста на «какой именно код» сверх двух.** Код возврата обязан быть из
   диапазона 0..=255, иначе `ExitCode::from` усечёт: `Some(code) => (code & 0xFF)`.
   Неуспех `cargo test` — это 101, помещается, но проверять надо сам факт ненуля, а не
   конкретное число, потому что cargo может вернуть и 1, и 101, и 4 в зависимости от
   того, чем именно сломалось.

## Границы

- **Правок PolyForge отсюда нет.** Список `RED_GATES` должен совпасть с тем, что
  владелец добавит в allowlist; расхождение означает, что обёртка готова, а
  аттестация — нет. Это F-08, отдельный репозиторий.
- **Не трогать `scripts/worker/validity_gate.py`, `run.sh` и пакет INFRA-03**, который
  сейчас в работе: там своя инверсия вердиктов, не путать с инверсией кодов.
- **Не выводить в отчёт «Verified» для RED-пакетов, пока патч F-08 не смержен.**
  Обёртка даёт возможность, а не факт. Формулировка в отчёте — «локально подтверждено,
  аттестуемо после мержа F-08».
- `TASKS` и `usage()` не переписывать: список доступных имён печатается из таблицы, и
  новая таблица должна попасть в подсказку, иначе задача будет не discoverable.
