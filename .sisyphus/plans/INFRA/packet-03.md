## Контекст

- **Причина, по которой пакет существует.** Предикаты остановки у гейта и раннера были
  инвертированы: гейт отвергал `stop == "error"`, раннер отвергал всё кроме `Stop`.
  На трёх трассах из пяти гейт называл успешным прогон, который раннер называл
  невалидным. Владелец выбрал единое правило: **годен только объявленный успех**.
- Раннер по этой оси уже соответствует решению (`verdict_for` отвергает
  `stop != StopReason::Stop`), поэтому **правки раннера в этом пакете нет** — она
  в другом пакете, см. «Границы».
- `peak` из исходной формулировки правила вынесен владельцем в отдельную находку
  **F-21** и в пакет не входит: peak-guard из плана ночной сессии #4 до кода не
  дошёл, а подставлять заглушку вместо отсутствующей проверки нельзя.

## Проверки, замеренные на 5 трассах до написания пакета

Не предположено, а измерено replay'ом. Это и есть материал для регрессий:

| трасса | `stopReason` последнего `turn_end` | `agent_end`/`agent_settled` | финальный `message_end` | вердикт |
|---|---|---|---|---|
| canary-packet-03 | `stop` | 1 / 1 | `role=assistant`, usage есть | **valid** |
| skeleton-packet-01 | `stop` | 1 / 1 | `role=assistant`, usage есть | **valid** |
| cli-red-packet-03 | `toolUse` | 0 / 0 | `role=toolResult`, usage нет | invalid |
| taskfile-packet-02 (080409) | `toolUse` | 0 / 0 | `role=toolResult`, usage нет | invalid |
| taskfile-packet-02 (080839) | `toolUse` | 0 / 0 | `role=toolResult`, usage нет | invalid |

Три независимых признака — причина остановки, завершающий маркер агента и финальный
`message_end` — разделяют одни и те же две трассы от трёх. Это подтверждение, что
правило не выдумано, а совпадает с формой реальных потоков.

**Условие владельца выполнено:** завершающий маркер в трассах **есть**
(`agent_end` и `agent_settled` как типы событий), подбирать замену не пришлось.

## Что сделать

1. **Главное правило.** `Valid` возможно только если выполнены ВСЕ шесть условий:

   | # | условие |
   |---|---|
   | 1 | `stop_reason_last == "stop"` |
   | 2 | `pi_exit == 0` |
   | 3 | `timeout == false` — безусловно, а не только при `turns < 2` |
   | 4 | финальный `message_end` есть: последний `message_end` имеет `message.role == "assistant"` и `message.usage` |
   | 5 | трасса не оборвана: последняя строка — валидный JSON **и** присутствует `agent_end` либо `agent_settled` |
   | 6 | существующие проверки `loop` и `budget` — не трогать |

2. **`invalid_reason`, первым сработавший, в этом порядке:**

   ```
   timeout → error → aborted → incomplete_tool_use → unreported
   → no_final_message → truncated → loop → budget → nonzero_exit
   ```

   Имена — машинные токены, они попадают в `metrics.json` и будут читаться
   инструментами, поэтому пробелы и русский текст внутри поля недопустимы.
   Причина обязана называться: свёрнутая в «невалидно» ошибка неотличима от
   невалидности по любой другой причине (закон 6).

3. **`pi_exit` начать использовать.** Сейчас он читается из аргумента, попадает в
   JSON и печатается, но **не участвует ни в одном отказе** — то есть прогон с
   ненулевым кодом возврата гейт считает годным. Это правится здесь.

4. **`timeout` сделать безусловным.** Сейчас он влияет только на пару
   `timeout and turns < 2`. По правилу любой таймаут делает прогон негодным.

5. **`stop_reason_last` читать как сейчас.** Замерено: значение одинаково, если
   брать последний `stopReason` из всего потока или только из `turn_end`, и
   `stopReason` не встречается на `message_end` с `role=toolResult` ни разу. Правки
   не требуются — не переписывать работающее.

6. **Три replay-проверки перевернуть** в том же коммите, что и гейт, с причиной
   рядом с каждой: `# F-20: last stop=toolUse → invalid(incomplete_tool_use)`.
   Это не ослабление: эти три строки кодировали старую, отменённую семантику, и
   именно они были доказательством, что прогон, завершившийся посреди работы
   инструмента, проходил как успешный. После переворота они становятся
   доказательством, что исправление работает. Проверки, ожидавшие `true` и
   сохраняющие `true` (`skeleton`, `canary`), не трогать.

7. **Регрессии на синтезированных потоках** — обязательны, по одной на каждый
   `invalid_reason` из перечня п.2, плюс успешный случай. Синтез через уже
   готовый `mk_jsonl` в `run.sh`, потоки — маленькие и детерминированные.
   Отдельно и обязательно: **обе ветви `pi_exit`**. Сейчас `--pi-exit` не передаётся
   ни в одной из 34 проверок, поэтому условие `exit == 0` выполняется тривиально и
   никем не проверяется — проверка, которую не гоняют, выглядит выполненной.
   Нужны случаи `pi_exit=0` (годен) и `pi_exit=1` (`nonzero_exit`).

8. **Схему metrics не менять** сверх добавления `invalid_reason`. Ключи `valid`,
   `reasons`, `pi_exit`, `stop_reason_last`, `turns`, `tool_steps`, `timeout`,
   `total_input_cum`, `max_tool_steps`, `max_input_cum`, `tail_ok` остаются как
   есть. Новый тип verdict не вводится — это отдельный ADR, а не этот пакет.
   `run.sh` читает из вывода только `valid`, поэтому добавление поля безопасно.

## Границы

- **Правки раннера — не в этом пакете.** Пункты 2–5 требуют фактов, которых у
  раннера нет: кода возврата процесса, признака таймаута и факта обрыва. Он их
  получит только с телом запуска, которого пока нет — `RunRequest`/`RunOutcome` не
  строятся, и пути «трасса → вердикт» в раннере не существует. Пока этого нет,
  **совпадение вердиктов раннера и гейта на трассах недоказуемо**, и это остаётся
  открытым, а не объявляется выполненным.
- `stop_reason_of` в раннере не знает `toolUse`, поэтому при трактовке по Ф-18b
  прогон с таким финалом получит `Unreported`, тогда как гейт назовёт
  `incomplete_tool_use`. Вердикт совпадёт (оба — негоден), имя причины — нет.
  Это отдельная находка, здесь не чинится.
- `loop` и `budget` не переписывать: они работают и входят условием 6.
- Не трогать `crates/` вообще: пакет правит скрипты воркера, не крейты.
