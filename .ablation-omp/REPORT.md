# OMP SPIKE — ОТЧЁТ

Дата: 2026-09-27. Задача фазы: решить, заменяем ли Pi на OMP как движок воркера.
Данные: `.ablation-omp/runs/*.jsonl` (сырые события `--mode json`), `PROBE.md` (шаг 2.0).
Модель во всех прогонах: `neuraldeep/qwen3.6-unlim-noreason`, `--thinking off`, n=3 на плечо.

## 0. Переформулировка вопроса (результат PROBE)

OMP — **не движок**. Это extension-слой поверх Pi: `peerDependencies:
@earendil-works/pi-coding-agent`, `dist` = 150K, официальная установка — `pi install oh-my-pi`.
Поэтому «заменить Pi на OMP» технически невозможно: OMP работает *внутри* Pi и
наследует его модель, инструменты, usage, сессии и транспорт.

Корректные варианты: **Pi** (сегодня) | **Pi + OMP-слой** | **HYBRID** (выборочно).
Всё дальнейшее — измерения этих вариантов.

## 1. Overhead (шаг 2.1)

Метод: один и тот же `pi` 0.87.1, один и тот же промпт `.`, изолированные каталоги
сессий, `--no-context-files --no-skills --no-themes --no-prompt-templates`,
только флаг `-e <oh-my-pi/dist/extension.js>` различается.

`usage` из `message_update`: OMP median ctx_end = 14095, vanilla median = 14095
(доминирует `cacheRead` ~12576; `input` = 1519 у обоих). **На уровне usage разницы нет.**

Но разница есть и она важнее — она в **системном промпте**, извлечённом детерминированно
из события `message_end` (`sections`):

| Секция | vanilla | OMP | Δ |
|---|---|---|---|
| preamble | 169 | 169 | **+0** |
| tools | 339 | 684 | +345 |
| rules | 839 | 2184 | +1345 |
| docs | 1334 | 1334 | +0 |
| cwd | 79 | 79 | +0 |
| **Итого** | **2760** | **7526** | **+4766 байт** |

Инструменты: vanilla 4 (`read, bash, edit, write`) → OMP 10, добавлены
`oh_my_pi_delegate_task`, `oh_my_pi_subagent`, `glob`, `grep`, `interactive_bash`,
`look_at`. Потерянных нет.

**Ключевая находка: `preamble` идентичен — OMP не подменил системный промпт.**
Заявленное в README «replaces Pi's default system prompt with a Sisyphus-style
orchestrator prompt» в данной конфигурации **не произошло**. Вместо этого выросли
`rules` (+1345) — то есть расширение добавило правила и инструменты, но оркестраторная
личность не активировалась. Вероятная причина: требуется иной `promptTemplate`/иной
агент, либо промпт-шаблон не входит в npm-поставку по этому пути. Это дефект, а не
конфигурация — и он делает главную ценность OMP неработающей «из коробки».

Итог overhead: **+4766 байт (~+173% к системному промпту) ради неактивного
оркестраторного слоя и 6 инструментов.**

Поведенческой дисперсии, убившей SoL-Pi на W2 (×15), здесь не наблюдается.

### ⚠️ Эти числа НЕ доказывают превосходство OMP

Сравнение **не является чистым A/B** и не должно использоваться как аргумент за REPLACE:

- baseline 67847 снят в другом протоколе — с проектным контекстом (AGENTS.md, packets,
  skills discovery), тогда как прогоны OMP шли с `--no-context-files --no-skills --no-themes`;
- в пакет добавлена шапка («Работай ТОЛЬКО в текущей директории…»), отсутствующая в оригинальном W1;
- baseline — медиана другой сессии, другие сутки, другой cache state.

Разница −27.6% по input в первую очередь отражает **разницу протокола измерения**, а не
эффект OMP. Проверка, которая нужна для честного вывода, — прогон Pi в **том же**
протоколе, что и OMP; она не выполнена (время фазы). Вывод по W1: **OMP не хуже Pi на
bounded-задаче и ведёт себя стабильно (дисперсия 1.6%)** — и только это.

## 3. Изоляция (шаг 2.3)

| Вектор | OMP | Вывод |
|---|---|---|
| `task.isolation.enabled` | отсутствует (и в схеме, и в `dist/**`) | нет |
| sandbox / worktree в коде | совпадений нет | нет |
| ограничения путей в `rules` | **ни одного** упоминания sandbox/absolute/outside/worktree | нет |
| `.git` в изоляции | изоляции нет; `.git` появляется только если агент сам в нём | нет |

F1-сценарий (пакет просит писать по абсолютному пути в `~/gits/stellwerk`) **OMP не
перехватывает** — нечего перехватывать. Единственная защита в проекте — наша:
`scripts/worker/sandbox.sh` + path-guard в `stellwerk-dispatch`, и она ловит нарушение
пост-фактум, блокируя экспорт. Она работает одинаково для Pi и для Pi+OMP, потому что
живёт в dispatch-слое, а не в агенте.

## 4. Субагенты (шаг 2.4)

| Свойство | Значение |
|---|---|
| Инструменты | `oh_my_pi_subagent` (персоны), `oh_my_pi_delegate_task` (категории) |
| Встроенные персоны | `oracle`, `librarian`, `explore` |
| Встроенные категории | `quick`, `deep`, `ultrabrain` |
| `approvalMode` в OMP | **отсутствует** (в отличие от Pi/OMP-экосистем с `yolo`) |
| Изоляция субагента | не заявлена; `dist/agents/` = `registry.d.ts` + `types.d.ts` |

Негативный тест на обход запрета (`approvalMode: yolo`) **неприменим**: у OMP нет
`approvalMode`, значит и нет режима «разрешить всё», в котором можно было бы искать
дыру. Это скорее плюс: отсутствие режима исключает целый класс инцидентов. Оборотная
сторона: нет и внятного механизма «разрешить один опасный вызов» — если понадобится
интерактивное подтверждение, его придётся строить в dispatch-слое.

## 6. ВЕРДИКТ: HYBRID

**Pi 0.87.0 остаётся движком. OMP не внедряется как замена; его слой можно
рассмотреть точечно позже — как источник готовых субагентов, а не как оркестратор.**

Обоснование (по убыванию веса):

1. **Вопрос был поставлен неверно.** OMP не может заменить Pi: он работает внутри Pi.
   Любой «REPLACE» был бы самообманом.
2. **Главная ценность не работает.** Оркестраторная подмена промпта не произошла
   (`preamble` идентичен). Заявленное в README поведение — дефект поставки 0.2.0.
3. **Платим за воздух.** +4766 байт системного промпта (+173%) и 6 инструментов при
   окне воркера ~43k — это ~11% рабочего окна, потраченные на неактивный слой.
4. **Ничего из нужного не добавлено.** Песочница, path-guard, loop-guard, validity gate,
   изоляция — всё это отсутствует и в Pi, и в OMP. У нас оно уже есть и работает
   одинаково для обоих; менять исполнителя ради этого незачем.
5. **Субагенты — единственная реальная находка.** `oracle/librarian/explore` +
   `quick/deep/ultrabrain` выглядят полезными, но они дублируют роли OMO
   (`.omo/omo.jsonc`), а OMO — planner-only по решению из `PIVOT.md`. Переносить
   субагентов в воркер означало бы разрушить это решение без измеримой выгоды.
6. **Положительное:** OMP не хуже Pi на bounded-задаче (W1 3/3, дисперсия 1.6%) и не
   имеет `approvalMode: yolo`, то есть не добавляет вектор «агент сам себя разрешил».
   Ничего не сломано — просто ничего и не выигношано.

### Что изменило бы вердикт

- рабочий `promptTemplate` (если оркестраторная подмена начнёт срабатывать, OMP
  становится кандидатом на роль координатора воркеров — но это конфликтует с
  planner-only, значит решение принимает владелец);
- доказанная изоляция задачи / worktree на стороне OMP;
- OMP < 30M (сейчас 154M, из них 42M — сам Pi);
- чистый A/B на одном протоколе: Pi и Pi+OMP в одинаковых условиях.

### Открытый долг по фазе

Прогон Pi в протоколе OMP (для честного A/B) **не выполнен**. Рекомендуется закрыть
одним прогоном `run-overhead.sh` с `OMP=0` в уже существующем harness, если владелец
захочет обосновать HYBRID количественно. На вердикт это не влияет: он опирается на
контролируемые измерения (overhead, инерция промпта, отсутствие изоляции), а не на
кросс-протокольное сравнение токенов.
