# INT1 — первая встреча репозиториев

Два репозитория встречаются РОВНО ОДИН РАЗ: через artefact + evidence. Не через общий
рабочий каталог, не через общий worktree, не через правку чужого lockfile.

## Железное правило разделения

Ни один пакет не меняет оба репозитория. INT1 — не пакет и не исключение: это
исполняемый сценарий, в котором каждый шаг принадлежит ровно одному репозиторию.

| Шаг | Репозиторий | Что делает |
| --- | --- | --- |
| 1 | Riegel | Публичный код: выбран один пункт из B-03 (truthful-docs) или B-08 (coverage) |
| 2 | Stellwerk | Один реальный Run чинит эту мелочь; результат — артефакт + evidence |
| 3 | Stellwerk | Артефакт публикуется по release/revision + registry (I8) |
| 4 | Riegel | СВЕЖИЙ gate проверяет ЭТОТ результат: {snapshot, политика, набор, инструмент+версия, результаты, digest, исполнитель} |
| 5 | Riegel | Вердикт достаточности/недостаточности возвращается в диспетчерскую |

## Почему именно так

Шаг 4 — первое место, где проверяется B2 и B3 по-настоящему. Bootstrap-аттестация
(`cargo --version`) не может быть приложена к артефакту Stellwerk: у неё нет привязки
ни к снимку, ни к исполнителю. Если свежий gate принимает результат Stellwerk —
значит привязка работает. Если отвергает — значит политика действительно ловит слабое
доказательство, а не просто существует.

## INT1-A: DEFERRED до M7

**Решение владельца 2026-10-06.** Сквозной сценарий в M6 ограничен B-стороной: Stellwerk
прогоняет реальный пакет над Riegel, а свежий Riegel-gate (B-02 + B-03) проверяет
результат. Обратное направление — Stellwerk как проверяемый — в M6 **невозможно**:

`INT1-A` требует, чтобы Riegel проверил результат Stellwerk. Для этого Riegel должен
проверять чужой пакет, а не свой, и чтобы проверка имела смысл, проверяемый код должен
быть наблюдаем из Riegel. Ни того, ни другого в M6 нет: у Stellwerk нет
`ToolAttestation`-совместимого наблюдаемого наружу, а Riegel не знает, что такое
Stellwerk-Run.

Поэтому в M7: `INT1-A` возвращается вместе с условием «M5 runtime получает реального
потребителя», то есть когда появятся и наблюдаемая поверхность, и непустой runtime.

## Условия запуска

- [ ] A-01…A-06 выполнены и прошли negative-тесты и mutation gate.
- [ ] B-04, B-05, B-06 выполнены: привязка вердикта, отказы политики, identity+отзыв.
- [ ] Публикация артефакта идёт через release/revision + registry (не копированием файлов).

## Критерий приёмки INT1

> PASS прогона Stellwerk **И** свежий Riegel-gate, привязанный к этому конкретному
> snapshot / policy / identity, а не к bootstrap.

Обратный результат — тоже результат. Если gate отвергает корректный артефакт из-за
неверной привязки, это дефект B-04, а не повод ослабить политику.

## Запрещено

- общий worktree между репозиториями (I7 + правило разделения);
- «проверим позже, приложим текущие 5 записей»;
- принятие результата, принесённого агентом как JSON, вместо результата проверяющего;
- переход на новый Riegel вручную правкой `modules.lock`.

## Интеграционные инварианты, которые INT1 обязан проверить на себе

| Инвариант | Как проверяется здесь |
| --- | --- |
| I1 `git add` только явных путей | коммит артефакта из пакета, без `-A` |
| I2 отсутствие данных ≠ успех | Riegel-вердикт «нет данных» не превращается в PASS |
| I3 Verified только ToolAttestation | артефакт Stellwerk не Verified без реальной аттестации |
| I4 mutation ≥80%, источник outcomes.json | применимо к правке в Riegel |
| I8 источник истины = план-каталог | артефакт публикуется из пакета, не из зеркала |
| I10 verifier вне контроля verified | Riegel-gate проверяет артефакт, а не доверяет автору |
