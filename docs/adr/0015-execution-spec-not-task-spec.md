# ADR-0015: программа агента — отдельная `ExecutionSpec`, а не поле `TaskSpec`

Статус: принят
Дата: 2026-10-12
Решение владельца: 2026-10-11, п. 1 — `TaskSpec` **не расширяется**;
  вводится отдельная явная `ExecutionSpec` на стороне orchestration; CLI выбирает
  разрешённый engine-профиль; профиль сохраняется в Run; нет конфигурации — отказ
  **до** запуска; скрытый default запрещён.
Пакет: N1-02
Находка: BLOCKER 1 ревью N1 — добавление полей в `TaskSpec` ломает компиляцию
  workspace, а приёмка этого не видит.

## Проблема

Rust-путь запуска не мог назвать программу агента: у `TaskSpec`
(`crates/stellwerk-core/src/contract.rs:296`) нет ни `program`, ни `engine`.
Соблазн — добавить два поля туда — стоит дорого и стоит молча.

**Причина.** У `TaskSpec` **нет `Default`**, и все его поля обязательны. Два новых
обязательных поля ломают **каждый** литерал `TaskSpec { .. }` в дереве:

| файл | строка |
|---|---|
| `crates/stellwerk-task/tests/lifecycle.rs` | 23 |
| `crates/stellwerk-task/tests/inbox.rs` | 19 |
| `crates/stellwerk-task/tests/events.rs` | 19 |
| `crates/stellwerk-store/tests/status_transition.rs` | 15 |
| `crates/stellwerk-store/tests/task_crud.rs` | 14 |

Ни один из этих файлов не входит в `files_allowed` пакета N1-02. Исполнитель либо
нарушает пакет, либо оставляет workspace несобираемым.

**Хуже: приёмка этого не замечает.** Узкая команда `cargo test -p stellwerk-task
--test …` собирает **один таргет**; ошибка компиляции в чужих тестах её не касается.
А сверка baseline ищет строки `test … FAILED` — **ошибка компиляции таких строк не
порождает**. Пакет выглядел бы зелёным при разрушенном workspace. Это ровно тот
класс, ради которого решение 7 объявляет exit code обязательным.

## Почему `TaskSpec` — не то место

`TaskSpec` — это **что сделать**: цель, рабочее место, потолки, политика
доказательства. Программа агента — это **чем выполнить**. Это разные вопросы, и
смешать их значит протащить знание о запуске в контракт задачи и в `store`, который
этот контракт хранит. `store` не должен знать, каким бинарником запускается агент:
он хранит задачу, а не конфигурацию рантайма.

Отдельный тип заодно снимает вопрос `Default`: у `ExecutionSpec` его тоже нет и не
будет, но ломать чужие литералы он не может — его никто, кроме orchestration, не
строит.

## Решение

1. Вводится `stellwerk_task::execution::ExecutionSpec` — отдельный тип на стороне
   task, поля `program` и `engine`. Поля **без `Default`** и **без
   `#[serde(default)]`**: отсутствие поля это ошибка разбора, а не пустая строка.
2. **Реестр разрешённых engine-профилей живёт в коде**, не в конфиге репозитория.
   Конфиг правится тем же PR, что добавляет движок, и самовыдача разрешения стала бы
   неотличима от решения. Выбранный профиль захватывается в
   `ResolvedExecution`/`RunExecution` **до** запуска и сохраняется в Run, чтобы
   evidence показывал именно тот профиль, которым запускали, а не перечитанный позже.
3. **Нет конфигурации — отказ до запуска.** Три состояния различимы своими
   вариантами `ExecutionRefusal`: `Absent` (спецификации нет), `EmptyProgram`
   (`program` пуст), `UnknownProfile { engine, … }` (движок вне реестра). Скрытого
   default, `unwrap_or` и «нет ответа — запустим что настроено» не существует.
4. Отказ возвращается из `resolve`, у которого нет ни `Command`, ни песочницы: ни
   один процесс не стартует, отказ физически предшествует запуску.

## Почему это честно, а не формальность

Три состояния названы **разными вариантами**, а не одним `Err(String)`: «нет
спецификации», «спецификация есть, но пуста» и «движок не разрешён» чинятся
по-разному, и одно, выданное под видом другого, — это и есть дефект, против которого
написан закон 6 `AGENTS.md`. Пустой реестр (`EngineRegistry::of(&[])`) валиден и
отказывает **всему**: «не разрешено ничего» отличимо от «разрешено всё». Реестр,
принимающий любой движок, реестром не является.

## Что запрещено

1. **Добавлять поля `program`/`engine` в `TaskSpec`.** Он заморожен решением 1.
2. **Скрытый default.** Ни `Default` у `ExecutionSpec`, ни `#[serde(default)]`, ни
   «движок по умолчанию», ни пустая строка вместо отсутствующего поля.
3. **Реестр в конфиге репозитория.** Перечень разрешённых профилей задаётся в коде.
4. **Отказ после старта.** Проверка обязана стоять до `run_once` и до создания
   песочницы; отказ «по факту» не защищает ничего.

## Когда пересматривается

Если `TaskSpec` когда-нибудь получит `Default` (отдельным пакетом с
`contract-change` и ADR), вопрос о месте полей можно переоткрыть. Пока `Default` нет
и пять чужих литералов на месте, `ExecutionSpec` остаётся отдельной.

## Что НЕ делает этот ADR

- Не подключает CLI к `ExecutionSpec`: это N1-03/N1-10. Здесь только контракт-типы,
  реестр и `resolve`.
- Не решает, как реальный Pi получает модель: это N2-00 (model-transport).
- Не трогает `TaskSpec`, `taskfile.rs` и любой другой файл вне `files_allowed`.
