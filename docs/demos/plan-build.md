# Демо: сценарий Plan → Build (срез N1)

Сценарий: владелец вводит цель для небольшого изменения в репозитории, Stellwerk
разговаривает с **настоящей** моделью, показывает план и версию задачи, человек
**явно** утверждает версию плана, после чего Build должен выполнить одну задачу.

Статус среза (обновлён N2-00h3d/00h3e, живой прогон 2026-10-22): **Plan — реальный.
Build — реальный и запускается по `b`**, но под политикой C: чтение разрешено, запись и
оболочка запрещены до эффекта. Ход не начнётся без токена
`$XDG_CONFIG_HOME/stellwerk/neuraldeep.token` (0600).

## Команды

```sh
cargo build -p stellwerk-cli --bin stellwerk
./target/debug/stellwerk plan /path/to/repository
```

`plan` — подкоманда `stellwerk` (`crates/stellwerk-cli/src/main.rs`). Сессия
хранится в `<repository>/.stellwerk/plan/session.json` и переживает перезапуск.
Запись атомарна: `save_session` пишет `<repository>/.stellwerk/plan/session.json.tmp`
и делает `rename`, поэтому оборванная запись не оставляет частичный `session.json`.

## Что делает экран

`render_plan` (`crates/stellwerk-cli/src/plan.rs`) — чистый шов: `View` → строки,
без терминала и сети. Проверяется в памяти (`crates/stellwerk-cli/tests/plan.rs`).

Клавиши в живом цикле (`run_plan_tui`):

| Клавиша | Действие |
|---|---|
| ввод + `Enter` | задать цель и уйти в первый запрос к модели |
| `Esc` | отменить текущий запрос к модели |
| `a` | **утвердить текущую версию плана** (единственный источник утверждения — это действие человека) |
| `r` | запросить правку плана (перейти к ответу) |
| `b` | запустить Build: копия дерева, `pi` в `bwrap` без сети, гейт на каждый инструмент |
| `Ctrl-C` | выйти |

## Точка утверждения

Ответ модели — это текст, а не решение. `PlanSession::approve()` вызывается
**только** по нажатию `a`. Утверждение привязано двумя ключами: к значению
`version` (растёт на `set_goal`/`set_draft`) и к **SHA-256 канонического текста
плана** (`approved_digest` против `plan_digest()`). Поэтому изменённый после
утверждения план **снова требует** человека — в том числе правка полей черновика
в обход `set_draft`, когда счётчик `version` не двигается. Тесты на это:
`a_model_claim_of_approval_does_not_approve_anything`,
`a_changed_draft_after_approval_requires_a_new_approval`,
`changing_plan_text_without_bumping_the_version_still_requires_approval`,
`absent_summary_and_empty_summary_are_different_texts`.

Утверждение привязано и к снимку дерева: при загрузке сессии `run_plan_tui`
вызывает `reconcile_snapshot`, который сверяет сохранённый `snapshot` с текущим
`git HEAD`; при расхождении `version` растёт и утверждение сбрасывается — план,
утверждённый для одного дерева, не действует на другом. Тесты:
`a_snapshot_drift_after_approval_forces_reapproval`,
`a_matching_snapshot_leaves_approval_intact`.

## Живой прогон (зафиксировано этой сессией)

Транспорт — узкий доверенный канал:

```sh
OPENCODE_CONFIG=<scratch>/stellwerk-planner.json \
  opencode run --pure --format json --agent stellwerk-planner "<prompt>"
```

`current_dir` — нейтральный временный каталог; процесс `Stellwerk` держит канал,
а не песочница исполнения. Промпт (`build_prompt`) просит строго один JSON-объект
(`{"kind":"question",...}` или `{"kind":"plan",...}`), прямо запрещает модели
объявлять утверждение и **честно** описывает её возможности: репозиторий читать
нельзя, рабочий каталог пуст, плануй по тексту.

Наблюдавшийся прогон (`/tmp/opencode/smoke-repo`, цель
`Fix add() in lib.rs so it adds instead of subtracts.`):

* модель вернула JSON-план; `parse_reply` разобрал его в `PlanDraft`;
* экран показал поля плана и `версия: 2 / утверждена: —` с кнопкой
  `[ A ] утвердить эту версию плана (ждёт утверждения)`;
* после `a`: `stage: утверждён`, `версия: 2 / утверждена: 2`,
  `[ утверждено человеком ]`;
* после `b`: `Build: ходов модели N · заявок в гейт M · вывод: <первые 240 символов>`;
* `session.json` записан с `"version": 2`, `"approved_version": 2` и
  `"approved_digest": "<sha256 канонического текста плана>"`.

## Ограничения (явные, не замаскированные)

1. **Build запускается, но под политикой C.** Живой прогон 2026-10-22:
   `ходов модели 1 · заявок в гейт 0`. Копия дерева легла в
   `/tmp/stellwerk-build-<pid>/work` (без `.git`, с расширением
   `stellwerk_transport.ts`), целевой репозиторий не изменился — только
   `.stellwerk/`. Модель в этом прогоне инструментов не просила, поэтому запрет
   оболочки живым ходом **не** проверен: он доказан тестами
   `tests/build_runner.rs` (настоящий `pi` в `bwrap`, `touch` отклонён,
   канарейка не создана). Отсутствие заявок — факт прогона, а не доказательство
   политики.
2. **Вывод Build напечатан началом, а не сутью.** В `--mode json` первые 240
   символов — заголовок сессии; ответ модели лежит дальше (FINDING: брать
   последнюю реплику ассистента, а не префикс).

2. **Шлюз free-tier требует read-инструмент.** Конфигурация планировщика
   (`PLANNER_CONFIG_JSON`) выключает `bash`, `edit`, `write`, `patch`, `task`,
   `webfetch`. Если выключить **все** инструменты, включая `read`, запрос
   получает `403 FreeTierError: can only be used from within OpenCode`;
   конфигурация с одним `read` — принимается. Поэтому включён ровно один
   инструмент — `read`. **Ограничение `read` рабочим каталогом наблюдалось живьём**
   (запрос `read /etc/hostname` вернул tool error), но **внутри репозитория не
   форсируется**: гарантия держится на шлюзе среды и нейтральном `current_dir`,
   а не на нашем коде (FINDING). Мутирующие, исполняющие и сетевые инструменты
   выключены — это и есть инвариант «нет raw bash/edit/write».

3. **Планировщик не видит целевой репозиторий в этом срезе.** Канал запускается
   в нейтральном временном каталоге (чтобы не тянуть проектную конфигурацию
   целевого репозитория), а `read` ограничен рабочим каталогом. План строится по
   тексту цели и снимку `git HEAD`, а не по чтению дерева репозитория. Это
   сознательная граница безопасности среза.

## Мутационная проверка

Критическая чистая логика (разбор ответа, версионирование и утверждение,
персистентность, рендер, промпт) проверена `cargo-mutants`: на редакции **до**
привязки утверждения к SHA-256 — **50 мутантов, 46 убито, 4 нежизнеспособны,
0 пропущено — 100 % жизнеспособных убито**. Область задана явно (`--re`) по
чистым функциям; транспорт и цикл событий TUI (`LiveTransport`, `plan_loop`,
`handle_key`, `run_plan_tui`) исключены как непокрываемые юнит-тестами и
проверяются живым прогоном. Порог владельца — `>= 75 %` (ADR-0019); при этом
`missed > 0` разбирается отдельно и сам по себе не блокирует гейт. Привязка к
`plan_digest()` добавлена **после** этого замера и покрыта тестами из раздела
«Точка утверждения»; повторный замер той же областью — отдельная задача
(FINDING), а не молча заниженный или завышенный процент.

## Негативная гарантия

Модель не может изменить файловую систему. В живом прогоне запрос «создай
`pwned.txt`» завершился текстом, и файл **не** появился (проверено `ls`).
Структурно это закреплено тестом
`planner_config_grants_no_mutating_execution_or_network_tool`.
