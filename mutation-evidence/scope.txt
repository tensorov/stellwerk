Mutation scope: crates/stellwerk-task/src/runner.rs and crates/stellwerk-task/src/orchestrator.rs

Command flags: -f runner.rs -f orchestrator.rs

Why these two files:
  The N1/F8 fix (commit 57f11e6) lives entirely in these two modules. runner.rs
  owns `authorize` (the single decision point that reads the trusted registry and
  builds the CallRequest) and `record` (the receipt writer that persists the
  APPLIED risk). orchestrator.rs owns `risk_for_in` / `StaticRegistry` (the
  production registry lookup) and `SandboxWorker::preflight` (the gate record).
  A mutation in either file is exactly a regression of the property under test:
  "the effective tool risk comes from the registry, not from the caller's
  declaration, and unknown/errored lookups never execute."

Why not the whole crate:
  Scoping to the two changed modules keeps the mutant set focused on the fix and
  keeps the run bounded. Other modules (events, evidence, lifecycle, m5/*) are
  untouched by 57f11e6 and their mutants would dilute the signal.

Note on `-t 300`:
  `-t 300` is the per-mutant timeout in seconds (cargo-mutants 27.1.0). It is NOT
  a test filter. `-- <name>` would be a cargo TEST FILTER, not a file scope; it is
  deliberately not used here.
