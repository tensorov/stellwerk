# M3 — документ для human review. НЕ РАЗДАВАТЬ ВОРКЕРУ.

Дата: 2026-09-27. Milestone: M3 (gateway / RBAC-прокси). Статус: **12 пакетов написаны,
ни один не запускался и не отдавался воркеру.**

## Почему этот документ существует

M3 — первый milestone, где цена ошибки измеряется не падением теста, а **лишними
правами агента**. Ошибка в `permission_for` или в `decide` не роняет сборку: она
тихо разрешает то, что должна была запретить. Такие дефекты дешевле поймать
человеком до раздачи 12 пакетов, чем откатывать после.

Ниже — ровно то, что должны решить пакеты, изложенное так, чтобы решение было
принимаемо без чтения кода.

## 1. Итоговая матрица `risk_class × policy_level × verdict`

Единая таблица. Она **буквально идентична** разделам «Единая таблица
`risk_class` — источник истины» в `.sisyphus/plans/M1/packet-05.md` и
`packet-06.md` (63 строки, сверено md5 `c4d378235c3e70186343ba65ff49da8f`) —
правило перенесено из M1, чтобы M3 не изобретал вторую лестницу.

| risk_class | min_policy_level | verdict | что означает | пакеты |
|---|---|---|---|---|
| R0 | `L0Local` | **Allow** | чтение, эффекта нет | M1-05, M1-06, M3-02 |
| R1 | `L2Contributor` | **Allow** | запись в песочницу, откатывается её удалением | те же |
| R2 | `L3Maintainer` | **Ask** | сетевой выход: наружу уходят данные | те же |
| R3 | `L4Admin` | **Ask** | доступ к секретам: решает человек | те же |
| R4 | `L5Owner` | **Deny** | внешний наблюдаемый эффект (PR, публикация) | те же |
| R5 | `L5Owner` | **Deny** | необратимое разрушение | те же |

Лестница `Action → min PolicyLevel` (вторая, ортогональная ось, из M1-05):

| action | min PolicyLevel | пакет |
|---|---|---|
| `ReadWorkspace` | `L0Local` | M1-05 |
| `WriteWorkspace` | `L2Contributor` | M1-05 |
| `RunTask` | `L2Contributor` | M1-05 |
| `UpdateModule` | `L3Maintainer` | M1-05 |
| `ManageMembers` | `L4Admin` | M1-05 |
| `GrantRoles` | `L5Owner` | M1-05 |

### Правило композиции (M3-04, `gate::decide`)

```
effective_level   = max(permits_min(action), risk_table[risk].min_policy_level)
effective_verdict = Deny, если любой из двух вердиктов == Deny
                    иначе Ask, если любой == Ask
                    иначе Allow
allow             = (caller >= effective_level) AND (effective_verdict == Allow)
```

**`Deny` абсолютен: не эскалируется уровнем, даже `L5Owner`.** Владелец может
разрешить конкретное действие явно, но это отдельный вызов, а не следствие таблицы.
Это единственное место в системе, где «достаточно прав» перестаёт означать
«можно действовать».

## 2. Какие инструменты попадают в R4/R5

| инструмент | класс | вердикт | обоснование |
|---|---|---|---|
| `git push`, создание PR через `gh pr create` | **R4** | Deny | эффект виден другим людям; песочница его не откатит |
| `cargo publish`, запись в реестр пакетов | **R4** | Deny | то же + необратимость версии |
| `git push --force`, `git reset --hard` | **R5** | Deny | переписывает историю, откат только вручную |
| удаление данных вне песочницы | **R5** | Deny | необратимо |
| изменение политик (`GrantRoles`) | — | таблица | `L5Owner`; **не** классифицируется как R4/R5, потому что это про полномочия, а не про данные |
| сетевой вызов (`curl`, MCP-запрос наружу) | R2 | Ask | по умолчанию наружу уходят только public-данные |
| чтение `auth.json`, расшифровка токена | R3 | Ask | человек решает; ключи не попадают в чек (только хеши) |
| запись в песочницу | R1 | Allow | откатывается удалением песочницы |
| чтение | R0 | Allow | эффекта нет |

**Намеренно вынесено за пределы R4/R5:** `Allow` для инструментов из реестра
модулей. Модуль в `modules.toml` несёт собственный `risk` (`R0…R5`), и gateway
берёт его, а не назначает свой. Иначе риск, объявленный при регистрации модуля,
молча игнорировался бы.

## 3. Что gateway ГАРАНТИРУЕТ

1. **Каждый вызов получает чек.** `receipt.rs` (M3-09, M3-10): хеш входа, хеш
   выхода, вердикт, риск, длительность. Чек пишется **в том числе для
   запрещённых вызовов** — иначе «тихие» попытки не видны в расследовании.
2. **Секреты не попадают в чек.** В `Receipt` идут только sha256 от тел, никогда
   сами тела. Это проверяется тестами M3-10.
3. **Вывод ограничен 2k токенов** (`shaping.rs`, M3-05/M3-06). Полное тело
   уходит в артефакт, в контекст — хеш и путь. Хеш считается по **полному** выводу
   до обрезки, иначе ссылка на артефакт непроверяема.
4. **Инструмент вне монтажа не вызывается.** `session.rs` (M3-11) проверяет
   «инструмент смонтирован?» **до** `decide`: незамонтированный инструмент не
   должен даже думать о правах.
5. **Монтаж ограничен бюджетом контекста** (`mount.rs`, M3-07/M3-08), сумма
   стоимости смонтированных не превышает бюджет, порядок детерминирован
   `(cost_tokens, name)`.
6. **Personal-данные не уходят провайдеру с чужим retention** — это уже работает
   в M1-04 (`DataClass::permits_model`), gateway лишь вызывает предикат, не
   дублируя правило.

## 4. Чего gateway НЕ ГАРАНТИРУЕТ

Здесь важно быть точным: часть защит выглядит сильнее, чем она есть.

1. **`path-guard` ≠ изоляция на уровне namespace.** Песочница — `git archive` в
   `/tmp` **без `.git`**, плюс блокировка абсолютных путей репозитория в промпте и
   post-flight проверка, что репозиторий не тронут. Это работает, но это
   **обнаружение и блокировка, а не изоляция**: процесс воркера технически имеет
   доступ к файловой системе хоста. Настоящая изоляция (podman/bubblewrap,
   namespace) — в `DEFERRED`, её нет. В M3 gateway не добавляет изоляции: он
   фильтрует вызовы, а не ограничивает системные вызовы.
2. **Субагенты не наследуют решение.** `oh_my_pi_subagent` / `oh_my_pi_delegate_task`
   (найдены в OMP-спайке, `.ablation-omp/REPORT.md`) выполняют работу внутри
   процесса агента. Решение `decide` принимается **до** запуска, и если субагент
   внутри делает дополнительные вызовы, они не проходят через `decide` повторно.
   **Это дыра**, и её не закрывает ни один пакет M3.
3. **Секреты, попавшие в аргументы вызова, не очищаются.** `receipt` их не
   логирует, но и `input` инструмента не санируется: если модель передала токен
   в аргумент `bash`, gateway увидит это как R3-вызов и спросит — но к моменту
   вопроса токен уже предъявлен инструменту.
4. **`Ask` без подтверждения = `Deny`**, и это намеренно. Следствие: в
   неинтерактивном прогоне любой R2/R3-вызов **заблокирован**. Если M2 runner
   окажется неинтерактивным, легитимные сетевые задачи станут невыполнимыми.
5. **Запрет R4/R5 не заменяет разумность владельца.** Таблица запрещает
   `git push`. Она не мешает сделать то же самое через `bash -c` с недетектируемой
   формулировкой, если инструмент не классифицирован.
6. **Согласие не привязано к объекту.** `Ask` — это булево «спросили и получили
   да». Нет модели «это разрешено для этого вызова, но не для следующего».

### Поправка к сводной таблице

Сводная таблица, присланная владельцем вместе с ответами, оказалась неточным
пересказом по памяти, а не намеренной ревизией: в ней R0 шёл как `L1`, R1 —
как `read_external`, R2 — как `L2`/`write_local_draft`, R5 — без уровня.
**Источник истины — M1-06.** Авторизованы ровно две правки: R3 `L4Admin → L5Owner`
и вердикт R4 `Deny → Ask`. Остальное (`R0=L0Local`, `R1=L2Contributor` (запись
в песочницу), `R2=L3Maintainer` (сетевой выход, `Ask`), `R5=L5Owner` `Deny`)
— **без изменений**.

Отдельно отвергнуто предложение считать R1 «внешним чтением» с `Allow`:
внешнее чтение — это канал **входа** недоверенных данных в контекст модели
(prompt injection), и безусловный `Allow` на него для неинтерактивного воркера
понижает защиту. Отдельный класс для чтения из allowlisted-источников — вопрос
будущего дизайна со своим review, а не правка вдогонку к В1/В5.

## 5.1 Исходные формулировки вопросов (сохранены)

Каждый ответ меняет пакеты M3. Без ответов раздавать M3 преждевременно.

**В1. R4/R5 — всегда `Deny`, или допускаем `Ask` с подтверждением?**
Сейчас `Deny` абсолютен, даже при `L5Owner`. Альтернатива: R4 → `Ask` при
`L5Owner`, R5 остаётся `Deny`. Влияет на M3-02, M3-04, M3-11.
*Моё мнение:* текущий вариант безопаснее, но он делает `create PR` невозможным
из агента вообще — а это половина смысла `cmd_update`.

**В2. Что делает gateway, если инструмент не классифицирован?**
Сейчас: `risk.unwrap_or(R0)` в `mount.rs` и `permission_for` исчерпывающий `match`
(новый класс заставит компилятор спросить). Но «инструмент известен, риск не
проставлен» — это другое. Нужен ли явный **deny по умолчанию** для
неклассифицированных инструментов? Влияет на M3-02, M3-07.

**В3. Принимаем ли дыру с субагентами (п. 4.2) в M3, или это блокер?**
Если блокер — нужен пакет, запрещающий субагентов при `risk >= R2`.
Влияет на M3-01 (список запретов) и M3-11.

**В4. `Ask` в неинтерактивном прогоне: блокировать или доверять?**
Сейчас блокирует. Но M2 runner (`runner.rs`, M2-10) запускает Pi неинтерактивно.
Значит первый же легитимный сетевой вызов задачи упадёт. Влияет на M3-04, M3-11,
а также на конфигурацию M2-10. **Это мой главный вопрос: возможно, он делает M2
и M3 несовместимыми по объёму Ask.**

**В5. Уровень для `R3` (секреты) — `L4Admin` или выше?**
`L4Admin` может читать секреты, но не может менять роли. Для федерации, где
`Big Pickle` ограничен public-данными по retention policy, доступ администратора
к секретам может быть слишком широким. Влияет на M1-06 (уже реализован —
тогда потребуется изменение) и M3-02, M3-04.
