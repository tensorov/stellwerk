## Механизм дефекта — ИСПРАВЛЕН, исходная формулировка была неверной

Первая редакция утверждала: «два тест-бинарника параллельно = гарантированный FAIL».
**Это невозможно по конструкции cargo:** каждый `--test` target запускается как ОТДЕЛЬНЫЙ
процесс, а `std::env::set_var` действует только внутри своего процесса. Два бинарника
не могут разделить глобальный env. Заявленное воспроизведение «20/20» этим механизмом
объяснить нельзя.

**Реальная гонка — ВНУТРИ одного бинарника.** `tests/inbox.rs` содержит два разных теста,
тронувших одну переменную:
- `empty_inbox_env_is_an_error_not_a_silent_default` (`inbox.rs:247`) — `set_var("")` (строка 249);
- `missing_inbox_env_falls_back_to_workspace_path` (`inbox.rs:262`) — `remove_var` (строка 264).

Cargo запускает тесты внутри бинаря многопоточностью по умолчанию, поэтому эти два теста
**гоняются друг с другом**. Вот это и есть дефект.

**Агент не воспроизвёл гонку:** 16 прогонов (`--test-threads=1` и по умолчанию, по 8
каждый) дали 0 FAIL. Значит гонка проявляется только при конкретном чередовании потоков
и носит характер флака, а не устойчивого падения. RED обязан быть получен честно: пакет
не может объявить себя зелёным по построению.

**Почему это всё равно дефект, а не вкусовое.** Два теста, меняющих глобальное
изменяемое состояние в одном процессе, — это нестабильность по построению: результат
зависит от планировщика. То, что 16 прогонов прошли, доказывает лишь малую вероятность,
а не отсутствие гонки.

## Про `grep` в приёмке — критерий был невыполним

Приёмка требовала нулевого `grep 'set_var|remove_var' tests/`, но `tests/sandbox.rs:117,120,121`
лежит ВНЕ `files_allowed`. Критерий недостижим по построению: пакет не может сделать grep
нулевым, не тронув файл, который ему не принадлежит. Требование снято; проверка сужена до
файлов пакета, а `sandbox.rs` вынесен в отдельный F-79b.

## Про «одна точка входа»

`cli.rs` и `main.rs` в `files_allowed` не входят, а `cli.rs` переменную `STELLWERK_INBOX`
не читает вовсе. Формулировка «env-чтение остаётся ТОЛЬКО в точке входа» в текущем виде
непроверяема. Сужено: пакент убирает env-ЧТЕНИЕ из библиотечного кода (`approval.rs:125`)
и передаёт путь параметром; перенос чтения в `cli.rs` — отдельная задача, потому что этот
файл пакету не принадлежит.

## Контекст — дефект, а не вкусовое

`approval.rs:125` читает `std::env::var(INBOX_ENV)` в БИБЛИОТЕЧНОМ коде, а
`tests/approval.rs:129` делает `set_var(INBOX_ENV, …)`. Второй тест-бинарник —
`tests/inbox.rs:249,252,253,264,267,268` — делает то же самое шестью вызовами на ту же
переменную. Глобальное изменяемое состояние, разделяемое двумя бинарниками, есть
классический источник взаимного влияния: два параллельных бинарника гарантированно
FAIL.

Тот же класс в `sandbox.rs`: `src/sandbox.rs:52` читает `STELLWERK_SANDBOX`,
`tests/sandbox.rs:117,120,121` его пишет. Мина та же — просто ещё не взорвалась.

`tests/approval.rs:124` содержит комментарий, что переменная трогается «намеренно». То
есть риск зафиксирован и принят, но не устранён.

## Что сделать

1. `inbox_dir()` принимает путь параметром (`Config` или аргумент).
2. Чтение env убирается из библиотечного кода целиком. `cli.rs`/`main.rs` в пакет НЕ входят,
   и `cli.rs` переменную сейчас не читает — перенос чтения во вход приложения отдельная задача.
3. Тесты создают путь через `tempdir` и не трогают `std::env` вовсе.
4. То же для `STELLWERK_SANDBOX`, **если влезает в лимит трёх файлов.**

## Про `sandbox.rs` — граница пакета

`sandbox.rs` — четвёртый файл, а лимит ADR-0003 равен трём. Если он не влезает,
это **F-79b отдельным пакетом**, а не расширение этого. Молча включить четвёртый файл
значит нарушить ADR-0003; молча выбросить `sandbox.rs` — оставить мину на месте.
Правильный исход: `sandbox.rs` вынесен и зафиксирован как отдельный пункт.

## Проверка — по решению владельца 2026-10-06

- **RED — честно:** гонка **флакающая**, воспроизводится планировщиком потоков, а не
  постоянно. Агент не воспроизвёл её ни в одном из 16 прогонов. Пакет обязан либо получить
  настоящий RED, либо прямо сказать, что RED не получен, — и **не может** объявить себя
  зелёным по построению.
- **GREEN:** ноль `set_var`/`remove_var` в **файлах пакета** (не во всём `tests/`: там лежит
  `sandbox.rs`, который пакету не принадлежит), плюс **50** прогонов `cargo test -p
  stellwerk-task --test inbox` без FAIL.

**Честная оговорка.** Агент не воспроизвёл падение: три последовательных запуска дали
0 FAILED. Механизм дефекта подтверждён чтением кода, но конкретный способ воспроизведения
(параллельный запуск бинарников, иной раннер) должен быть назван владельцем или получен
на RED. Если пакет не может показать RED, он обязан это сказать, а не объявить себя
зелёным по построению.
