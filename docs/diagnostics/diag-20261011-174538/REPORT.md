## 1. Чем Stellwerk является СЕЙЧАС

**OBSERVED.** Stellwerk сегодня — **библиотека хорошо написанных и хорошо протестированных деталей без сборки**. Каждый тип в цепочке исполнения агента имеет проходящие тесты и **ноль production-вызовов**.

Единственная пользовательская поверхность — бинарник `stellwerk` из `stellwerk-registry`, и это **менеджер реестра модулей**, а не оркестратор:

```
main.rs:2 → cli.rs:153 → dispatch cli.rs:99
  module add | measure | audit | update
```

Из четырёх подкоманд реально работает одна: `module audit` (spawn реального MCP-сервера, JSON-RPC, таймаут, reap дочерних процессов, тесты).

**OBSERVED.** Второй бинарник `stellwerk-task` объявляет `#[command(name = "stellwerk")]` — **коллизия имени** с первым. Оба нельзя установить одновременно. Подкоманды `cancel` и `logs` — заглушки с `exit 1` (`cli.rs:131-132`).

## 6. Дефекты, мешающие первому Plan → Build в TUI

1. **`TaskSpec` не содержит имени программы агента.** `contract.rs:296-311`. TUI нечего запускать даже когда он написан. Это блокер №1.
2. **Нет coordinator, scheduler, delegation, interview, plan, summary.** Ноль совпадений по `scheduler|coordinator|queue|dag`. Для них **нет исходного кода** — это greenfield, а не «проводка».
3. **`run_once` не вызывается ниоткуда в production.** Нужен один production-оркестратор, владеющий `impl Worker`.
4. **`cancel`/`logs` — заглушки.** Пауза, остановка, возобновление отсутствуют.
5. **`EvidenceLedger` — трейт без единой реализации.** Ни в src, ни в тестах.
6. **Нет привязки evidence к снимку.** `chain_tail` хеширует поля записей; нет commit SHA, tree hash, digest рабочего дерева.
7. **Коллизия имён бинарников** — prerequisite для установки любого из них.
8. **Нет канала ответа.** `CallVerdict::Ask` фиксируется как `ANSWER_PENDING` навсегда.
9. **Нет daemon/background-режима** — Run переживает закрытие UI только потому, что его нет.
10. **`NetworkPolicy::allows` не вызывается** нигде в src.
